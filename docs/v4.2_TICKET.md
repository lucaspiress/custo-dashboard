## 4. Modelo de dados

### `campos_calculados`

```sql
CREATE TABLE IF NOT EXISTS public.campos_calculados (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    dataset_id BIGINT NOT NULL REFERENCES public.datasets(id) ON DELETE CASCADE,
    nome TEXT NOT NULL,
    formula TEXT NOT NULL,
    dependencias_json JSONB NOT NULL DEFAULT '[]'::jsonb,
    ordem INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_campos_calculados_dataset ON public.campos_calculados(dataset_id);
```

**Nota:** apenas datasets numéricos (não virtuais) podem ter campos calculados. Validação no endpoint POST.

## 5. Parser sandbox — Lista branca

### Funções permitidas

```
SUM, AVERAGE, IF, CONCAT, DATE, SUMIF, COUNTIF, MIN, MAX
```

### Operadores permitidos

```
+, -, *, /, =, >, <, >=, <=, &
```

### Literais permitidos

- Números: `123`, `45.6`, `0.5`
- Strings: `"abc"`, `'abc'` (aspas duplas ou simples)
- Datas: `DATE(2026, 1, 5)`

### Identificadores permitidos

- Apenas nomes de colunas existentes no schema do dataset (validados em tempo de criação da fórmula).

### Implementação

- **Lexer**: tokeniza a fórmula em tokens (`NUMBER`, `STRING`, `IDENT`, `OP`, `LPAREN`, `RPAREN`, `COMMA`).
- **Parser**: recursivo descendente. Gramática:
  ```
  expr       := or_expr
  or_expr    := and_expr (OR and_expr)*
  and_expr   := not_expr (AND not_expr)*
  not_expr   := 'NOT' comparison | comparison
  comparison := concat ((=|>|<|>=|<=) concat)?
  concat     := add ((& add)*)
  add        := mul ((+|-) mul)*
  mul        := unary ((*|/) unary)*
  unary      := '-' primary | primary
  primary    := NUMBER | STRING | DATE '(' ... ')' | IDENT | IDENT '(' args ')' | '(' expr ')'
  ```
  (Adaptar conforme necessário; `IF` e funções agregadas viram `IDENT '(' args ')'`).
- **Avaliador**: percorre a AST. Para cada nó:
  - `NUMBER` → float
  - `STRING` → str
  - `IDENT` → consulta valor da coluna na linha atual
  - `IDENT '(' args ')'` → dispatch para função da lista branca
  - Operadores → operação binária/unária

### Segurança

- **Nenhum `eval`/`exec`** em lugar nenhum.
- Identificadores fora da lista de colunas do dataset são rejeitados.
- Funções fora da lista branca são rejeitadas.
- Profundidade máxima de aninhamento: 10 (defesa contra stack overflow).
- Tamanho máximo da fórmula: 500 caracteres.
- Detecta e rejeita: `__import__`, `;`, `[`, `]`, `{`, `}`, `\`, acesso a atributos `.` (exceto dentro de números como `3.14`).

### Funções a implementar

```python
SUM(*args) → number          # soma todos os args (aceita números ou refs a colunas)
AVERAGE(*args) → number      # média
MIN(*args) → number
MAX(*args) → number
COUNT(*args) → number        # contagem não-vazia
IF(cond, then, else) → any   # condicional; cond é expr booleana
CONCAT(*args) → string       # concatena strings (converte números)
DATE(year, month, day) → date string ISO
SUMIF(range, criteria_sum, criteria?) → number  # aceita range como coluna, criteria como coluna ou valor
COUNTIF(range, criteria) → number               # idem
```

## 6. Endpoints (todos exigem login)

```
GET    /api/datasets/{did}/campos-calculados              lista campos do dataset
POST   /api/datasets/{did}/campos-calculados              cria campo. Body: {nome, formula}
PATCH  /api/datasets/{did}/campos-calculados/{cid}        atualiza nome/formula (valida novamente)
DELETE /api/datasets/{did}/campos-calculados/{cid}        remove campo
```

**Importante:** Apenas datasets numéricos (não virtuais). Validação retorna 400 se dataset_id for virtual.

**Validação:** ao criar/atualizar, executa o parser com a lista de colunas válidas do dataset (vinda do `schema_json` ou das linhas reais). Se parse falhar, retorna 400 com mensagem clara do erro (linha, coluna, tipo de token inesperado).

## 7. Drill-down (frontend)

### Comportamento

1. Usuário clica em uma barra de um widget de gráfico.
2. O ECharts `onEvents.click` captura o valor da barra (campo `x` + valor selecionado).
3. O estado do dashboard atualiza com um "filtro de drill" global: `{widget_origem_id: {campo: valor_selecionado}}`.
4. O `executarQuery` é chamado novamente com `drill_filters` no body (adicione essa chave se ainda não existir; o backend pode ignorar por enquanto na v4.2 e só aplicar nos widgets que não sejam o de origem).
5. Todos os widgets (exceto o de origem) recarregam com os dados filtrados.
6. UI mostra no topo: "Filtrado por: [campo = valor] [Limpar]".

### Endpoint `/query` (modificação)

Adicionar campo opcional ao body:
```json
{
  "widget_ids": [1, 2, 3],
  "slicer_values": {"1": ["valor1"]},
  "drill_filters": {"widget_origem_id": {"campo": "valor"}}
}
```

Backend aplica `drill_filters` aos widgets do dashboard que **não são o widget_origem_id** (evita auto-filtragem).

## 10. Notas para implementação

### Backend

- Reutilize padrão de `datasets_store.py` para `campos_calculados_store.py`.
- Para o `formula_parser.py`, **não use libs externas** (`formulas`, `pycel`, etc — decisão do usuário). Escreva do zero.
- O agregador (`agregador.py`) deve carregar `campos_calculados` do dataset e **incluir como colunas disponíveis** no `data_json` retornado — isso requer carregar `campos_calculados` antes de processar linhas.

### Frontend

- Para drill-down, use `echarts-for-react` `onEvents={{ click: handler }}`.
- Estado de drill pode ser um único objeto no `useState` do `DashboardBuilderPage`.
- Editor de fórmula pode ser um `<textarea>` simples com preview (não precisa de syntax highlighting nesta fase).
- Mantenha o lazy-load (`DashboardBuilderPage` já está em chunk separado).
